1. Executive Summary
KIO is a lightweight modular autonomous orchestration operating layer built for constrained consumer
hardware. It coordinates adaptive tool execution, contextual workflows, and cloud-AI inference through a
disciplined single-brain architecture.
What KIO is

A Python-native autonomous agent runtime

A cloud-inference orchestration layer (brain in the cloud, body local)

A resource-disciplined tool execution coordinator

A personal productivity OS for a single user on a single machine
What KIO is NOT

A chatbot or conversational assistant

A local LLM runtime

A multi-agent swarm

A LangChain wrapper

A Jarvis clone

2. Final Architectural Philosophy
2.1 Core Tenets
Tenet 1 — Cloud Brain, Local Body
All reasoning, intent parsing, and planning routes through a cloud LLM API (Gemini 2.0 Flash or
equivalent). KIO never loads a local language model. The local process handles orchestration,
tool execution, memory, and I/O — never reasoning.
Tenet 2 — Everything Through Core Brain
No module, tool, observer, or plugin executes anything autonomously. Every execution path runs
through Core Brain's routing layer. There are no sidechannels, no direct tool calls, no bypass
paths.
Tenet 3 — Lazy is Law
Any module consuming > 10 MB that is not needed at startup is lazy-loaded on first use and
unloaded after use. The baseline process must remain under 120 MB at idle.
Tenet 4 — Explicit Over Implicit
Tool execution contracts are typed. Side effects are declared. Destructive operations require
explicit confirmation. Nothing happens invisibly.
Tenet 5 — Stability Over Features
A working, stable Gate N is worth more than a broken Gate N+2. Feature gates are locked until
prior gates pass all tests.
2.2 Architectural Contradiction Resolution
The following conflicts were found across prior audit materials and resolved here:
Conflict
Resolution
Event-driven pub/sub vs Centralized orchestration
Centralized orchestration wins. Lightweight internal event bus for notifications only — never for execution routing.
Multi-agent swarms vs Single core brain
Single Core Brain. Multi-agent adds concurrency bugs and RAM explosion on 8 GB hardware.
Local LLM (Llama/Mistral) vs Cloud inference
Cloud inference only in v1–v3. Local LLM requires ≥ 4 GB RAM minimum — incompatible with idle target.
Always-on observers vs Lazy loading
Lazy loading wins. No observer runs at idle unless it costs < 5 MB.
Vector DB for memory vs SQLite
SQLite wins. Vector DB (ChromaDB, Qdrant) consumes 200–500 MB resident. SQLite with FTS5 is sufficient for v1–v2.
LangChain vs Custom lightweight orchestrator
Custom orchestrator. LangChain imports alone consume 80–150 MB. Unacceptable.
Plugin-as-microservice vs Plugin-as-file
Plugin-as-file with restricted namespace. No subprocess mesh.

Core Brain triggers replanning when:
1
Verifier returns FAIL with replan=True
2
Tool execution raises ToolPermissionDenied or ToolSandboxViolation
3
LLM response is malformed 2x in a row
4
User explicitly requests plan change mid-execution
5
A critical dependency tool is unavailable

6. Planner / Executor Model
6.1 Strict Separation Contract
Planner          → produces  → ExecutionPlan
ExecutionPlan    → consumed by → Executor
Executor         → produces  → ExecutionResult
ExecutionResult  → validated by → Verifier
Verifier         → produces  → VerificationReport
VerificationReport → read by  → Core Brain
These four components never call each other directly. All communication is via DTOs passed through
Core Brain.

6.3 Execution Flow
Core Brain
  │
  ├─► Planner.decompose(goal, context)
  │     └─► returns ExecutionPlan
  │
  ├─► [if requires_confirmation] → notify user → await confirm
  │
  ├─► Executor.run(plan)
  │     ├─► for each step (respecting dependencies):
  │     │     ├─► ToolRegistry.validate(step)
  │     │     ├─► ToolRegistry.execute(step)
  │     │     └─► collect ExecutionResult
  │     └─► returns list[ExecutionResult]
  │
  ├─► Verifier.validate(plan, results)
  │     └─► returns VerificationReport
  │
  └─► if replan → Core Brain.replan(report) → loop
      else      → Response.format(results) → dispatch
6.4 Retry Logic
async def execute_step_with_retry(step: PlanStep) -> ExecutionResult:
    for attempt in range(step.retry_budget + 1):
        try:
            result = await tool_registry.execute(step)
            if result.success:
                return result
        except ToolTransientError as e:
            if attempt == step.retry_budget:
                # Try fallback step if defined
                if step.fallback_step_id:
                    return await execute_fallback(step.fallback_step_id)
                return ExecutionResult(success=False, error=str(e), ...)
            await asyncio.sleep(2 ** attempt)   # Exponential backoff

7.2 Side Effect Classification
class SideEffectClass(Enum):
    NONE        = "none"         # Pure computation, no external effects
    READ        = "read"         # Reads external state, no mutations
    WRITE       = "write"        # Mutates state, reversible
    DESTRUCTIVE = "destructive"  # Mutates state, NOT reversible
Confirmation policy:

NONE / READ: Auto-execute

WRITE: Log but auto-execute (unless user has set confirmation mode)

DESTRUCTIVE: Always require explicit user confirmation before execution

8. Event System Decision
8.1 Decision: Centralized Orchestration + Notification Bus
Chosen: Centralized Core Brain orchestration + lightweight internal event bus for module notifications.
[All execution]        → Core Brain → [routes explicitly]
[Module notifications] → Internal EventBus (asyncio.Queue) → [subscribers]
The Internal EventBus is ONLY for:

Observer firing notifications ("clipboard changed", "file modified")

Watchdog health signals

Memory persistence signals

Module lifecycle events (loaded, unloaded)
The Internal EventBus is NEVER used for:

Tool execution routing

Plan dispatch

LLM call routing

Response delivery
8.2 Why Not Pure Event-Driven?
Pure event-driven pub/sub on this architecture leads to:
1
Event spaghetti: When module A emits, B handles, B emits, C handles — the execution graph
becomes impossible to trace.
2
Debug impossibility: Stack traces become meaningless. "Who triggered this?" requires event log
archaeology.
3
Race conditions: Asyncio event-driven systems with shared state require careful locking. The
extra complexity is not worth it at this scale.
4
Memory leaks from subscribers: Forgotten subscriptions cause accumulation.

8.3 EventBus Implementation
class KIOEventBus:
    def __init__(self):
        self._subscribers: dict[str, list[Callable]] = {}
        self._queue: asyncio.Queue = asyncio.Queue(maxsize=100)
    def subscribe(self, event_type: str, handler: Callable) -> None:
        self._subscribers.setdefault(event_type, []).append(handler)
    async def publish(self, event: KIOEvent) -> None:
        await self._queue.put(event)
    async def dispatch_loop(self) -> None:
        while True:
            event = await self._queue.get()
            handlers = self._subscribers.get(event.type, [])
            for handler in handlers:
                try:
                    await handler(event)
                except Exception as e:
                    logger.error(f"EventBus handler error: {e}")
            self._queue.task_done()
Queue maxsize=100 acts as backpressure. If events accumulate beyond 100, publishers block —
signaling a bottleneck rather than silently dropping events.

Purpose: Current session state, active task context, in-flight data. Storage: Python dict in-process.

11. Security Architecture
11.1 Authentication Boundaries
Local auth: Token file at ~/.kio/auth.token. File permissions: 600. Not stored in env vars. Loaded
once at startup, held in memory, never logged.
Telegram auth: Bot token in encrypted config. User ID allowlist — KIO only processes commands from
authorized Telegram user IDs.
API key management: Cloud LLM API key loaded from ~/.kio/secrets.json (file perm 600). Never
logged. Never included in error messages.

12.2 Plugin Loading Strategy
Plugin file placed in ~/.kio/plugins/
       │

14.2 Watchdog
class KIOWatchdog:
    HEARTBEAT_INTERVAL = 30   # seconds
    MAX_MISSED_BEATS = 3      # before restart attempt
    async def run(self) -> None:
        missed = 0
        while True:
            await asyncio.sleep(self.HEARTBEAT_INTERVAL)
            if not await self.core_brain.health_check():
                missed += 1
                logger.warning(f"Watchdog: missed beat {missed}/{self.MAX_MISSED_BEATS}")
                if missed >= self.MAX_MISSED_BEATS:
                    await self.attempt_restart()
                    missed = 0
            else:
                missed = 0

15.2 Memory Enforcement
import gc
import psutil
class ResourceGuard:
    SOFT_LIMIT_MB = 150
    HARD_LIMIT_MB = 190
    async def check(self) -> None:
        process = psutil.Process()
        ram_mb = process.memory_info().rss / 1024 / 1024
        if ram_mb > self.HARD_LIMIT_MB:
            # Emergency: unload all lazy modules immediately
            await observer_manager.unload_all()
            await plugin_manager.unload_all()
            gc.collect()
            logger.critical(
                f"RAM hard limit hit: {ram_mb:.1f} MB — emergency unload performed")
        elif ram_mb > self.SOFT_LIMIT_MB:
            # Soft: unload idle observers and plugins
            await observer_manager.unload_idle()
            gc.collect()
            logger.warning(
                f"RAM soft limit: {ram_mb:.1f} MB — idle modules unloaded")

17. Anti-Patterns to Avoid
Anti-Pattern
Why It Kills KIO
Direct tool calls bypassing Core Brain
Breaks audit trail. Creates hidden execution paths. Security hole.
Importing LangChain as convenience
80–150 MB import cost. Framework lock-in. Destroys RAM budget.
Always-on background threads per observer
Thread-per-observer = RAM bloat + OS scheduler overhead.
Vector DB for all memory
ChromaDB/Qdrant = 200–500 MB resident. SQLite FTS5 is 99% sufficient for v1–v2.
Multi-agent swarms for parallelism
On 8 GB RAM: each agent ~100 MB. Three agents = system swap.
shell=True in tool execution
Shell injection risk. Never use with any user-derived input.
Growing context window unbounded
LLM input cost explosion. Latency death spiral. Implement compression.
Plugin as microservice
Network overhead. Process management overhead. Not worth it at this scale.
Event spaghetti (pub/sub for execution)
Untraceable execution flow. Debug nightmare. Race conditions.
Optimistic concurrency everywhere
On a single async loop: unnecessary complexity. Be explicit with locks.
Premature local LLM integration
Any local model ≥ 4B params = ≥ 4 GB RAM. Breaks hardware budget. Gate to v4+.
God classes
Core Brain grows into 5000-line monolith. Keep it a router, not an implementer.

20. Final Engineering Verdict
What KIO is, precisely
A solo-deployable Python daemon that wraps cloud LLM reasoning around local tool execution, controlled
via Telegram and CLI, running on a standard laptop without ever requiring a local AI model, Docker, or a
framework dependency.
Is it buildable?
Yes. Every component in this document maps to a concrete Python module. No component requires
hardware beyond what's specified. No component requires a paid service beyond a cloud LLM API key
(Gemini free tier is sufficient for development).
What will kill it
1
Gate skipping. Attempting Gate 3 features before Gate 2 is complete will produce unmaintainable
spaghetti. The gates exist specifically because KIO's history shows an incompletion loop —
ambitious scope, fragmented execution.
2
Framework temptation. LangChain will look like a shortcut at Gate 1. It is not. Its import cost alone
fails the RAM budget.
3
Scope creep at Gate 0. The skeleton phase is boring by design. Resist adding features. Prove the
shell works first.
4
RAM budget drift. Check RAM after every gate. If it's trending toward the ceiling before Gate 4,
something is wrong and must be fixed before continuing.
Build Order Priority — Single Most Important Rule
Gate 0 COMPLETE before Gate 1 starts.
Gate 1 COMPLETE before Gate 2 starts.
Never run two gates in parallel.
