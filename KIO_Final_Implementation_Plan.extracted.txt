Full Repository Audit
Executive Assessment
kio_fixed_v3 is a functional prototype — not an orchestration runtime. It executes real commands, handles
multi-step flows, and resists framework creep. It cannot be called early-runtime because Core Brain, Planner,
Verifier, Memory, EventBus, Observer, and Lifecycle are all absent. The delta between current state and
Architecture v1.1 is large but bridgeable — the codebase is still small enough to refactor without rewriting.
Current Runtime Flow
INPUT → kio_bot.py:handle_message() [Telegram text]
→ asyncio.to_thread(route()) [thread offload]
→ command_router.py:handle_command() [string dispatch]
→ operator directly OR task_engine.run_task() [execution]
→ dict result [no verification]
→ flattened to string [Telegram reply]
MISSING: observe → reason → plan → execute → verify → adapt

SECTION 3
Final Security Model
Design Principles
Lightweight. Modular. No enterprise bloat. Every security mechanism maps to a concrete Python module under
200 lines. Security is enforced at runtime, not hoped for at design time.
4-Layer Permission Architecture
Layer 1: Tool Registration
tool.permissions_required declared at register time
unknown tool name → ToolRegistrationError (never execute)
Layer 2: Plan Approval (Core Brain)
brain.approve_plan(plan, user_profile)
checks each step's permissions vs user_permission_set
DESTRUCTIVE step without prior confirmation → block + notify
Layer 3: Execution Gate (Executor)
executor re-validates EVERY step before tool call
defense in depth: plan approval cannot be the only gate
Layer 4: Side Effect Confirmation
SideEffectClass.DESTRUCTIVE → hard block → notify user → await 'confirm'
timeout 60s → auto-cancel, log, notify

Hard-Blocked Operations (Permanent)
✘ eval() or exec() on any user-supplied or LLM-generated string
 
✘ subprocess.Popen(shell=True) with user-controlled input
 
✘ Recursive tool calls depth > 5
 
✘ Plugins writing to Core Brain internal state directly
 
✘ Network requests to localhost / 127.0.0.1 (SSRF prevention)
 
✘ Modifying ~/.kio/auth.token or secrets.json via any tool
 
✘ Spawning observer processes without ObserverManager registration
 
✘ LLM-generated tool name not in ToolRegistry → immediate reject

SECTION 5
Final Implementation Strategy
Core Methodology: Stabilization-First
Do not add features. Stabilize what exists. Then add components in gate order. Every gate requires passing
tests before the next gate opens. No exceptions. A broken Gate 1 with Gate 3 features is worse than a clean
Gate 0.
Implementation Phases
PHASE 0 Pre-work (before any code): [1 week]
■■ Fix .gitignore. Remove .venv from repo.
■■ Delete dead code: _lazy_import('ai'), dead YouTube branch, empty docs.
■■ Write requirements.txt with pinned versions.
■■ Create ~/.kio/ directory structure with secrets.json schema.
■■ Install: python-telegram-bot, httpx, psutil, aiosqlite.
PHASE 1 Gate 0 (Skeleton): [2 weeks]
■■ main.py entry point with state machine stub
■■ core/brain.py stub (no LLM yet)
■■ core/event_bus.py (drop-oldest, maxsize=500)
■■ core/config.py (loads ~/.kio/config.json)
■■ memory/manager.py (SQLite init + schema migration)
PHASE 2 Gate 1 (Core Brain + LLM): [2 weeks]
■■ core/llm_gateway.py (Gemini only, DEGRADED flag)
■■ core/brain.py full (intent routing, context, DEGRADED truncation)
■■ channels/cli.py (basic input)
PHASE 3 Gate 2 (Tool Registry + Execution): [3 weeks]
■■ tools/registry.py (KIOTool Protocol, ram_budget_mb)
■■ Wrap operators: app, browser, file, system
■■ planner/planner.py + executor/executor.py + verifier/verifier.py
■■ ResourceGuard.check_capacity() in executor
PHASE 4 Gate 3 (Memory + Telegram): [3 weeks]
■■ memory/episodic.py, semantic.py, goal_memory.py
■■ Memory pruning background task
■■ channels/telegram.py (clean, user allowlist)
PHASE 5 Gate 4 (Observer System): [3 weeks]
PHASE 6 Gate 5 (Plugin + Security): [4 weeks]
PHASE 7 Gate 6 (Production Hardening): [3 weeks]
How to Prevent Architecture Drift
Drift Pattern
Prevention
Core Brain grows into implementer
Monthly audit: brain.py line count > 400 = refactor signal.
Tool execution leaks outside Executor
All tool calls must appear in execution_log. Spot-check weekly.
AI tool generates wrong abstractions
AI generates module bodies only. Never architecture, never routing logic.
Gate skipping under time pressure
Gate N test suite is locked. CI blocks Gate N+1 if Gate N fails.
Framework temptation (LangChain)
requirements.txt is reviewed before every pip install.
EventBus used for execution
EventBus only processes KIOEvent types. No ExecutionPlan allowed in
queue.

How to Use AI Tools Safely
AI tools (Claude, Cursor, Gemini CLI) generate module bodies efficiently. They hallucinate architecture. Never

audit log. Review every AI-generated file line-by-line before merging. Run gate tests after every merge.

SECTION 11
Final Engineering Rules
These rules are permanent. Violation requires full architectural review before proceeding. No exceptions for
deadline pressure or development convenience.
MUST Always Follow
✓ Core Brain is the single execution router. No path bypasses it.
 
✓ observe → reason → plan → execute → verify → adapt loop is immutable. No step skipped.
 
✓ RAM targets are hard constraints. Feature that breaches them is blocked, not deferred.
 
✓ Tool contracts are typed. No dynamic, untyped tool execution at any gate.
 
✓ Audit log is append-only. No deletion API ever.
 
✓ Gates are sequential. Gate N tests pass before Gate N+1 starts.
 
✓ Every lazy-load calls ResourceGuard.check_capacity() before loading.
 
✓ EventBus is notification-only. Never route execution through it.
 
✓ DEGRADED mode handles gracefully. Never crash when LLM is unreachable.
 
✓ Watchdog attempt_restart() implemented before Gate 6.
 
✓ Memory pruning runs on schedule. No ad-hoc pruning.
 
✓ Verifier confidence floor 0.6 enforced. Never silently succeed low-confidence plan.
 
✓ DESTRUCTIVE operations require explicit user confirmation. Always.
 
✓ Secrets never logged. Never in error messages. Never in code.
 
✓ AI-generated code reviewed line-by-line before commit.
 
✓ Gate test suite locked. CI blocks advancement on test failure.
 
MUST NEVER Add
✘ Local LLM before v4 (hardware upgrade required)
 
✘ LangChain, LlamaIndex, or any heavy framework
 
✘ Vector database (ChromaDB, Qdrant, Weaviate) before v4
 
✘ Multi-agent architecture or autonomous agent swarms
 
✘ Always-on camera, persistent OCR, always-on audio before v3
 
✘ subprocess mesh for plugins
 
✘ eval() or exec() on user-controlled input — ever
 
✘ Blocking EventBus publishers
 
✘ Thread-per-observer model
 
✘ RAM-unchecked lazy-loads
 
✘ Gate skipping under any circumstances
 
✘ Merging AI-generated security code without human review
 
✘ .venv committed to repository
 
✘ Secrets in any tracked file
 
Architecture Drift to Prevent
■ Core Brain growing into implementer (God class). Monitor: brain.py > 400 lines = refactor.
 
■ Tool execution leaking outside Executor via helper functions.
 
■ Memory system growing vector embeddings before v4.
 
■ Observer system accumulating always-on observers not in approved list.
 
■ Plugin system allowing simultaneous plugins before RAM budget expands.
 
■ EventBus used for execution routing as 'temporary' measure.
